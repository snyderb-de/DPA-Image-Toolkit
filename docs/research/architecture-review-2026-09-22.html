  • delete ~150 lines and one duplicate gate
  • two test patches vanish
  • interface shrinks: 6 progress keys, not 14

Problem. Half the worker sits on the loop and half re-implements it; request validation happens inside the thread; output roots are hidden state; Started.output_folder is unset so PDF jobs cannot be undone.

  • undo becomes possible for reduce / pdfa

  • delete ~80 lines, two helpers

sequenceDiagram
  participant Reg as registry
  participant App as app.py
  participant Run as JobRunner

  App->>Run: start(tool_id, started)

Problem. Typed Started fields are flattened into a string dict and dug out again by key in three files; the runner has learned worker attributes and registry keys, and the undo safety boundary is assembled ad hoc.

Solution. The runner stores the Started record; routes and the error report read typed fields. Prepared.data stays as the prepare-to-start stash only.

  • locality: "what undo may delete" defined once
  • runner stops probing worker internals
  • web tests stop seeding the dict by hand
  • leverage: one record, four readers

Top recommendation

1 · Put the OCR PDF worker on the shared batch loop, then 2

OCR is the hottest module in the log and the only worker still carrying its own loop and its own gate. Moving it onto run_file_batch removes the most duplicated behaviour for the least interface change, unblocks candidate 4 (every worker then fits one base), and drops two test patches. Candidate 2 is the same move for the last half-converted worker and makes PDF jobs undoable.
